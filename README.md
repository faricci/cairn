# Cairn

**A zero-infrastructure quality harness for coding agents.** Small sensors run the tools you already use, speak one JSON contract, and hand the agent a signal it can correct itself against, with a blocking gate behind it for when it doesn't.

[![License](https://img.shields.io/badge/license-Apache%202.0-blue.svg)](LICENSE) [![Python](https://img.shields.io/badge/python-3.11%2B-blue.svg)](https://www.python.org/downloads/)

## Why Cairn

Coding agents produce code quickly — not always correct code. Left unsupervised they stray: complexity climbs, security holes creep in, dead code and unused imports pile up, architectural boundaries erode. Reviewers become the only safety net, catching it one pull request at a time, too late and too slowly.

Cairn is the **harness** around the agent: a thin, deterministic feedback loop that catches those regressions *while the code is being written*, not after review or in production. Small **sensors** run the tools you already have — ruff, radon, pytest, cppcheck, layering rules — and emit one common signal the agent reads and self-corrects against. The same sensors become a blocking **gate** at commit and in CI, so if no agent ever reads a word of it the floor still holds, and human-written code is caught the same way. Adding a check means writing one wrapper script; the engine never changes.

## What it looks like

`cairn check` prints one line per sensor. When something fails it carries the guidance you configured (prefixed `→`), the concrete findings, and a trend arrow against the last snapshot — everything the agent needs to fix it without asking anyone:

```text
$ cairn check
[cairn] complexity   FAIL  14 (threshold 10)  ▲
  → Legacy hotspot. When you touch one of these functions, extract helpers to lower cc.
  etl/src/kpi_etl.py:42  cyclomatic complexity 14 in 'issues_to_raw_df' (max 10)
[cairn] lint         PASS  0  =
Scout rule: leave code cleaner than you found it.
```

The agent reads that, fixes the code, and re-runs until every line says `PASS` and the arrows point down. `cairn gate --stage pre-commit` prints the same signal but exits non-zero, so a failing sensor stops the commit.

Arrows: `▲` worse, `▼` better, `=` unchanged, `*` no baseline yet. The last line is the repo's optional `global_guidance`.

## Quickstart

<details>
<summary><b>Requirements</b> — Python 3.11+, plus whichever tools your sensors call</summary>

- **Python 3.11+** — the engine is stdlib-only (it uses `tomllib`).
- **`pip install radon ruff`** — for the two bundled Python sensors (`complexity`, `lint`).
- Optional: **`cppcheck`** on PATH for the C++ `lint-cpp` sensor.
- Optional: **`pip install pytest`** for the `tests` (QA) sensor.
- **git** — only if you want the pre-commit gate.

The engine itself needs no third-party packages; you only install the tools your sensors call.

</details>

Cairn has a **source** (this repo: engine + sensor wrappers + guides) and a **target** (any repo you want to harness). `cairn apply` copies a self-contained `.cairn/` folder into the target and **merges** a small managed pointer block into your agent instruction file(s) — it never overwrites existing content (see [Wiring it to your coding agent](#wiring-it-to-your-coding-agent)).

```bash
# 1. Get Cairn and put the wrapper on PATH (or call ./cairn by full path)
git clone <this-repo> cairn && cd cairn

# 2. Install the tools your sensors call
pip install radon ruff

# 3. Install the harness into your project
cairn apply --target /path/to/your/repo

# 4. Run the sensors (non-blocking; agent or human reads the guidance)
cairn check --target /path/to/your/repo

# 5. (optional) Record a baseline so trend arrows have a reference point
cairn snapshot --target /path/to/your/repo
```

`apply` also adds `.cairn/` to the target's `.gitignore`: the vendored engine is regenerated by `apply`, and keeping it out of git also keeps sensors from scanning Cairn's own code instead of yours.

Want to try it right now? A ready-made playground lives in [`examples/sample-repo`](examples/sample-repo) — it ships its `.cairn/cairn.toml` and `AGENTS.md`; `apply` vendors the engine and sensors into it, then `check` runs:

```bash
cairn apply --target examples/sample-repo
cairn check --target examples/sample-repo
```

## Prior art & how Cairn differs

Each neighbouring tool solves one slice:

| Tool | What it does | Limit |
|---|---|---|
| [wily](https://github.com/tonybaloney/wily) | tracks complexity over git history | Python only, complexity only |
| [import-linter](https://import-linter.readthedocs.io/) | enforces import/layer contracts | imports only |
| ArchCodex | architectural constraints for agents | needs `@arch` annotations in your sources |
| [CodeScene](https://codescene.com/) | code health, PR gates, MCP server | paid, hosted service |

**Cairn is the only one that is zero-infrastructure, speaks one JSON contract for any tool in any language, and lets you add a sensor in 20 lines.** One ledger, one config file, copy a folder.


Cairn is **not a full AI-DLC**. It is the **deterministic quality-control layer of the developer inner-loop** — the write → check → fix cycle — where enforcement is real tools with machine-checked pass/fail, not an LLM grading itself. It does not plan, design, or write code; it is the guardrail around whoever (agent or human) does. From that base it **extends toward QA**: the `tests` sensor (pytest) is a shipped example, and coverage/security scanners plug in the same way.

Compared to prompt-based AI-SDLC rulesets (e.g. AWS's [AI-DLC Workflows](https://github.com/awslabs/aidlc-workflows)):

- **Methodology-as-prompts** ship markdown rules the agent reads; verification is the **LLM grading itself** against those rules, and gating is an approval step. Broad scope: the whole lifecycle (requirements → design → code → QA).
- **Cairn** is a small deterministic **engine**: sensors run real tools (`ruff`, `radon`, `pytest`, `cppcheck`, ...), emit a machine-checked JSON contract, and a **blocking gate** stops the commit/CI on `fail`. Focused scope: the inner-loop quality control (maintainability + architecture today, QA sensors extending outward).

In one line: *Cairn enforces quality with real static-analysis and test tools plus a machine-checked blocking gate — not the LLM grading itself.* You can run it **underneath** a prompt-based methodology as its deterministic gate.

## Usage modes

`cairn check` runs sensors and prints a guidance-enriched summary the agent reads and self-corrects against (non-blocking). `cairn gate` is a thin blocking backstop for pre-commit/CI that reuses the same sensor definitions.

The same `cairn check` output is consumed by different actors. Who reads stdout — and can change code — decides the mode:

- **Agentic loop (primary).** `apply` merges a Cairn pointer into your agent instruction file(s) (`AGENTS.md`, Copilot, Cursor, ...), telling the coding agent to run `cairn check` after each change. The guidance-enriched stdout lands back in the agent's context, so it self-corrects and re-runs until PASS — a closed write → check → fix loop with no human.
- **Commit / CI gate (backstop).** The pre-commit hook (or a CI step) runs `cairn gate`. No agent involved: a blocking `fail` stops the commit/build. Deterministic safety net that also catches human-written code.
- **Human in the terminal.** You run `cairn check` yourself, read the guidance, and decide. Identical mechanics — your head is the context window. Best way to trust the harness before handing it to an LLM.

The guidance line is designed for a machine that then acts (agentic loop); in the manual mode it is just a helpful hint.

## Commands

```bash
cairn check    [--stage in-session] [--target DIR]
cairn snapshot [--target DIR]
cairn history  [--sensor ID] [--target DIR]
cairn apply     --target DIR [--check] [--source DIR]
cairn gate     [--stage pre-commit|ci] [--target DIR]
```

Run via the wrappers: `cairn.cmd` (Windows) or `./cairn` (bash).

## Configuration (`cairn.toml`)

`cairn apply` drops a starter `.cairn/cairn.toml` that declares the harness for the repo. A full example:

```toml
version = 1                       # required, must be 1

# Optional: define paths/values once and reuse them via ${name} in `run`.
[vars]
src    = "backend/src etl/src"    # space-separated paths become multiple args
max_cc = "10"

# Real bugs from ruff — block the commit.
[[sensors]]
id       = "lint"
run      = "python .cairn/sensors/ruff_sensor.py --select F ${src}"
category = "maintainability"      # maintainability | architecture | quality
stage    = ["in-session", "pre-commit"]   # in-session | pre-commit | ci
guidance = "Real bugs (unused imports/vars, bad f-strings). Remove or use them."

# Complexity — advisory only: shown in-session, never blocks a commit.
[[sensors]]
id       = "complexity"
run      = "python .cairn/sensors/radon_sensor.py --max-cc ${max_cc} ${src}"
category = "maintainability"
stage    = ["in-session"]
guidance = "Legacy hotspot. When you touch one of these functions, extract helpers to lower cc."

  # Optional per-sensor threshold, used to pick the trend direction.
  [sensors.threshold]
  metric    = "cc"
  value     = 10
  direction = "lower-is-better"    # lower-is-better | higher-is-better
```

| Field | Required | Meaning |
|---|---|---|
| `version` | yes | Config schema version (currently `1`). |
| `[vars]` | no | `name = value` pairs; reference as `${name}` in any `run`. An undefined `${...}` fails fast. |
| `[[sensors]].id` | yes | Unique sensor name (shown in output). |
| `[[sensors]].run` | yes | Shell command that prints the Sensor JSON Contract on stdout. |
| `[[sensors]].category` | yes | `maintainability` or `architecture`. |
| `[[sensors]].stage` | yes | Any of `in-session`, `pre-commit`, `ci`. `check` runs `in-session`; `gate` runs the stage you pass. |
| `[[sensors]].guidance` | no | Natural-language hint printed on failure — read by the agent to self-correct. |
| `[sensors.threshold]` | no | `metric` / `value` / `direction`; informs the trend arrow. |

## Sensors

A sensor is a small wrapper script that runs an existing tool and prints the **Sensor JSON Contract** (`status: pass|fail` + optional `score`/`findings`) on stdout. Adding a sensor never touches the engine.

| Sensor | Tool | Category | What it catches |
|---|---|---|---|
| `complexity` | [radon](https://pypi.org/project/radon/) | maintainability | functions with high yclomatic complexity |
| `lint` | [ruff](https://pypi.org/project/ruff/) | maintainability | Python bugs, unused imports/vars, tyle, import order |
| `lint-cpp` | [cppcheck](https://cppcheck.sourceforge.io/) | maintainability | C++ bugs, undefined behaviour, dead code |
| `layers` | stdlib `ast` | architecture | forbidden cross-layer imports |
| `tests` | [pytest](https://pypi.org/project/pytest/) | quality | failing/errored tests (the worked QA example) |

Wrappers live in `harness/sensors/`. Requirements: `pip install radon ruff` (the `layers` sensor is pure stdlib; `lint-cpp` needs `cppcheck` on PATH; `tests` needs `pip install pytest`).

> **Categories & scope.** Sensors are grouped by `category`: `maintainability` and `architecture` are shipped and proven; `quality` is the QA slice — `tests` (pytest) is the first worked example, and the same mechanism extends to coverage and security scanners (`bandit`, `semgrep`) by adding a wrapper. Security scanning is **not** bundled yet; treat it as a roadmap sensor you can add today.

### Language-agnostic by design

The engine only runs a command and reads the JSON contract from stdout, it knows nothing about Python. Other stacks just add their own sensor wrappers (the wrapper script may stay in Python; it only shells out to the native tool and translates the output):

| Stack | Example tools |
|---|---|
| Python | `ruff` (lint), `radon` (complexity) |
| C++ | `cppcheck`, `clang-tidy` |
| Java | `checkstyle` (lint), `pmd` (complexity) |

**Selecting which sensors run:**
- *One language per repo* — each repo keeps only its stack's sensors in `cairn.toml`. Already supported.
- *Polyglot monorepo* — one `cairn.toml`, each sensor pointed at its subtree, e.g. `run = "python .cairn/sensors/cppcheck_sensor.py services/native"`.

`cppcheck_sensor.py` ships as a worked non-Python example.

### Add a sensor

1. Write `harness/sensors/<tool>_sensor.py` that runs the tool and prints the contract JSON (see `ruff_sensor.py` for a tool that speaks JSON natively, `cppcheck_sensor.py` for one that needs output translation, or `pytest_sensor.py` for a QA/test example).
2. Add a `[[sensors]]` entry to `cairn.toml` with its `run` command, `category`, `stage`s, and self-correction `guidance`.

That's it: `check`, `gate`, `snapshot`, and `history` pick it up automatically.

### The Sensor JSON Contract

This is the stable interface between a sensor and the engine. A sensor prints **one JSON object** to stdout. Its **exit code is ignored** — `status` is the source of truth (so a tool that exits non-zero merely because it found issues still composes cleanly).

```json
{
  "sensor": "complexity",            // string, required
  "status": "pass",                  // "pass" | "fail", required
  "score": 14,                        // number, optional (the metric value)
  "threshold": 10,                    // number, optional
  "direction": "lower-is-better",     // "lower-is-better" | "higher-is-better", optional
  "findings": [                       // array, optional
    {
      "file": "etl/src/kpi_etl.py",  // string | null
      "line": 42,                     // number | null
      "message": "cyclomatic complexity 14 in 'issues_to_raw_df' (max 10)",
      "severity": "error"             // "error" | "warning" | "info"
    }
  ]
}
```

| Field | Required | Purpose |
|---|---|---|
| `sensor` | yes | Sensor id, echoed in output. |
| `status` | yes | `pass` or `fail` — the engine's decision comes from here, not the exit code. |
| `score` | no | The metric value; compared against the snapshot to compute the trend arrow. |
| `threshold` | no | The limit the score is judged against (informational in output). |
| `direction` | no | Which way is "better", so the trend arrow points correctly. |
| `findings[]` | no | Per-issue detail (`file`, `line`, `message`, `severity`). Printed to help the agent/human fix. |

If your tool cannot run (e.g. not installed), still emit contract-compliant JSON with `status: "fail"` and an `error`-severity finding explaining how to install it — the harness stays observable instead of crashing.

## Wiring it to your coding agent

The full working agreement is vendored as a single source of truth at `.cairn/guides/AGENTS.cairn.md` (refreshed on every `apply`). What actually reaches the agent is a small **managed pointer block**, merged non-destructively into your instruction file(s):

```markdown
<!-- BEGIN CAIRN (managed - do not edit inside this block) -->
## Cairn harness
... run `cairn check` before finishing; the gate blocks a failing commit ...
Full working agreement: `.cairn/guides/AGENTS.cairn.md`.
<!-- END CAIRN -->
```

Key properties, because a single root `AGENTS.md` is **not** universal:

- **Non-destructive merge.** If the file exists, only the block between the markers is inserted or updated; your own content is untouched. If it doesn't exist, it is created. Re-running `apply` is idempotent.
- **Agent-aware targets.** Different tools read different files. `apply` writes the block to the right place per agent:

  | `--agent`  | File written                          |
  | ---------- | ------------------------------------- |
  | `agents` / `codex` | `AGENTS.md`                   |
  | `copilot`  | `.github/copilot-instructions.md`     |
  | `cursor`   | `.cursor/rules/cairn.mdc`             |
  | `claude`   | `CLAUDE.md`                           |
  | `cline`    | `.clinerules/cairn.md`                |

- **Auto-detect (default).** With no `--agent`, `apply` always ensures `AGENTS.md` and additionally injects into any of the above files that already exist in the repo. Force a set explicitly with e.g. `cairn apply --target . --agent copilot --agent cursor`, or hit every location with `--agent all`.
- **Gate is the real guarantee.** Instruction injection is best-effort for the *proactive* in-session loop. Even if no agent ever reads it, the pre-commit/CI **gate** is deterministic and agent-independent: a failing sensor blocks the commit regardless. The loop degrades gracefully.

## Platform notes

- The pre-commit hook is a **Python** script (shebang `#!/usr/bin/env python`), not bash. This is deliberate: on locked-down Windows, git's bundled `bash.exe` is often blocked by policy (AppLocker/AV), which kills bash hooks. A Python hook runs via the allowed system interpreter.
- The hook needs a real `python` on PATH. On Windows, don't rely on the `python3` Microsoft Store alias; the hook uses the interpreter git resolves for its shebang.
- Where local hooks can't run at all, run the same gate in **CI** instead: `cairn gate --stage ci`. In-session `cairn check` still works locally regardless.

## Philosophy

Cairn started as the opposite of what it is now: a platform meant to cover the whole SDLC, install itself, and serve every role. It worked, and it was not worth maintaining. Every role covered was another thing to keep alive.

So the scope collapsed to one question: *when a team writes code with agents, what is the smallest thing that keeps the work on a shared path?* Four principles came out of that, and they are the whole design:

**Mark the direction, don't dictate the route.** The tempting answer to agent drift is a highly customised agent that knows your codebase, it has to be rebuilt for every team, every stack, every model. Cairn adds no linter, no complexity metric, no test runner, it gives the ones you already use a shared signal and a common gate.

**Your workflow is a config file, not a fork.** A repo declares its own harness in `.cairn/cairn.toml`: which sensors run, at which stage, against which threshold, with what guidance. Adapting Cairn to your process means editing that file, not patching the engine. Adding a check means writing one wrapper that prints the JSON contract (about twenty lines) and never touching the engine at all.

**Deterministic beats persuasive.** Instructions to an agent are best-effort. They help, and they are not a guarantee. Every rule that matters is also a sensor with a machine-checked pass/fail behind a blocking gate. If no agent ever reads a word Cairn writes, the gate still holds and it catches human-written code the same way.

**Assistant, not police.** The first job of a failing sensor is to tell you how to fix it, not to punish you. `check` is non-blocking and carries guidance; the gate is the backstop for what escapes. Prefer fixing the code over raising the threshold, and prefer raising a threshold over suppressing a sensor. A suppressed sensor never fires again.

Cairn is deliberately incomplete. It ships sensors for a Python-shaped process today as example, plus one C++ example to prove the engine is language-agnostic. The gap between that and your process is the point: it is meant to be filled by you.

## Roadmap / future directions

Cairn is intentionally small today; the design leaves room to grow along a few axes without changing the core write → check → fix loop:

- **MCP server.** Expose `cairn check`/`gate` as [Model Context Protocol](https://modelcontextprotocol.io) tools so MCP-capable agents call the sensors **directly**, with no instruction-file wiring and no shell parsing — the structured JSON contract flows straight into the agent's context.
- **More QA sensors.** Coverage thresholds and security scanners (`bandit`, `semgrep`) plug into the existing `quality` category exactly like the shipped `tests` (pytest) sensor.
- **Richer trends.** Persist per-sensor history to flag slow regressions (e.g. complexity creeping up over many commits), not just single-run pass/fail.
- **Config profiles.** Per-language / per-team `cairn.toml` presets seeded by `apply`.

These are directions, not commitments — issues and PRs welcome.

## Why the name

Above the treeline, where there is no path, **cairns** — stacks of stones — mark the safe line across broken ground. Almost every hiker has followed one; most never learned the name.

Two things make them the right metaphor. They *mark the way without altering the mountain*: a cairn does not build a road, it points at one that already works. And **no single person builds a cairn** — there is a Scottish habit of saying *"I'll put a stone on your cairn"*, and every walker who passes adds one. A cairn is collective knowledge, stacked over time, guiding whoever comes next and bringing you back down in the fog.

| On the mountain | In the harness |
|---|---|
| Ground with no path | the complexity of shipping software with agents |
| The cairn | shared checks that mark the safe line |
| Adding a stone | a new sensor, a tuned threshold, better guidance |
| Finding the way back in fog | `snapshot` + `ledger`: what changed, and when it drifted |
| A marked, protected line | the pre-commit and CI gate |

Cairn is far from perfect and far from complete. That is not an apology — it is the design. **It needs you to add a stone.**

> *Every team adds a stone; everyone finds the way.*

## Contributing

Cairn is intentionally small  and easy to extend.

**Add a sensor (the most common contribution).** Write `harness/sensors/<tool>_sensor.py` that runs a tool and prints the Sensor JSON Contract, then add a row to the Sensors table. Use `ruff_sensor.py` (tool speaks JSON) or `cppcheck_sensor.py` (needs output translation) as templates — no engine changes required.

**Work on the engine.** It lives in `cairnlib/` (config, sensors, state, report, install) with the CLI in `cairn.py`. Keep it dependency-free (stdlib only).

**Before opening a PR:**
1. Lint: `python -m ruff check --select E,F,I cairnlib harness`
2. Dogfood: `cairn check --target .` (Cairn harnesses itself — keep it green).
3. Keep changes focused, and update this README when you add a sensor, command, or config field.

**Guidelines:** stdlib-only engine; one wrapper script per sensor; the Sensor JSON Contract is the stable interface — don't break it. Discuss larger design changes in an issue first.

## Status

Working prototype: engine + `apply`/`check`/`gate`/`snapshot`/`history` and five deterministic sensors, validated end-to-end. A unit suite covers config validation, the sensor contract, and trend logic — run it with `python tests/test_cairnlib.py`. Cairn also harnesses itself: `cairn check --target .` should stay green.

## Security

`cairn check` runs the commands listed in `.cairn/cairn.toml`. Commands are executed directly (never through a shell), but they are still arbitrary commands: treat a repo's `cairn.toml` with the same care as any build script, and read it before running Cairn in a repository you do not control.
